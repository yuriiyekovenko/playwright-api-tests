## 1. Resource overview

An Owner has `firstName`, `lastName`, `address`, `city`, `telephone` (all required, writable) plus read-only `id` and `pets` (array of Pet, each with `visits`). The `/owners` path tree also hosts owner-scoped Pet and Visit operations. They are listed in the inventory; the Pets and Visits resources deserve their own designs, so only owner-scoping and cross-resource consistency are covered here.

Field constraints [DOC] (`OwnerFields`):

| Field     | Type   | Constraints                                                  |
| --------- | ------ | ------------------------------------------------------------ |
| firstName | string | required, 1..30, pattern `^[\p{L}]+([ '-][\p{L}]+){0,2}$`    |
| lastName  | string | required, 1..30, pattern `^[\p{L}]+([ '-][\p{L}]+){0,2}\.?$` |
| address   | string | required, 1..255                                             |
| city      | string | required, 1..80                                              |
| telephone | string | required, 1..20, pattern `^[0-9]*$`                          |
| id        | int32  | read-only, minimum 0                                         |
| pets      | Pet[]  | read-only, required in response                              |

Errors use `ProblemDetail` (`type, title, status, detail, timestamp, schemaValidationErrors[]`) [DOC]. Path `ownerId`/`petId` are int32, minimum 0 [DOC].

Security: the spec declares NO security scheme and no `401`/`403` responses [DOC], but the service returns 401 for missing or wrong credentials on every endpoint [OBS]. Only one role (admin) is configured in the framework; authorization by role is not testable [ASSUMPTION].

## 4. Existing coverage

- `tests/pet-types-api.spec.ts` covers PetTypes only.
- No owners client, types, factory or spec exists. Existing coverage of Owners: **none**.
- Framework facts: tests use `client` fixture; clients have `*Raw` and happy-path methods; the happy-path method asserts a status (so D2/D3 would fail inside `update`/`delete` if it is coded to the documented 200; expected status is 204, see Q1). `fakeId()` is a local helper in the PetTypes spec (2^30..2^31-1) and would need to be shared.
- Auth is applied globally through `httpCredentials`; unauthenticated tests need a separate request context without credentials.

## 5. Test data and conventions

- Every test creates its own owner(s) via `POST` (fully parallel runs, shared service). Seeded owners (ids 1..10) are read-only reference data; never modify or delete them.
- Factory `OwnerFactory.random()` (proposed): `firstName`/`lastName` letters only (the pattern forbids digits, so no UUID suffix; use `faker.string.alpha({length: 8})`-style values plus a random-letters suffix for uniqueness), `address`/`city` free text, `telephone` exactly 10 digits (D1).
- Unique `lastName` per test where `?lastName=` filtering is asserted, to avoid collisions in the shared dataset.
- Non-existent id: `2147483647` or the existing `fakeId()` range (returns 404 [OBS]).
- Clean-up: delete owners created by the test where cheap (owners deletion is available), without breaking parallel tests.
- Priority: P0 = core CRUD and contract, P1 = validation, boundaries, and error handling, P2 = edge/lenient behavior, sub-resources, observed-only.
- "Expected" column: **[DOC]** matches spec; **[OBS]** reflects the live behavior where spec is silent or contradicted. Scenarios whose expectation contradicts the spec are marked `KNOWN-DEFECT?` and should be written to the documented behavior (failing) once the reviewer confirms, not weakened.

### 9.2 Findings and evidence per question

**Root cause shared by Q3a/Q3b/Q3c/Q12.** [SRC] `rest/advice/ExceptionControllerAdvice.java` defines an `@ExceptionHandler(Exception.class)` that answers HTTP 500 with a `ProblemDetail` ("An unexpected error occurred while processing your request"). Only `MethodArgumentNotValidException` (400) and `DataIntegrityViolationException` (404) are special-cased. Every other exception, including Spring MVC's own client-error exceptions, therefore becomes a 500. [OBS] The `title` of each 500 names the exception: `ConstraintViolationException` (id `-1`, `size=0`), `MethodArgumentTypeMismatchException` (id `abc`), `HttpMediaTypeNotSupportedException` (Content-Type `text/plain`), `HttpMediaTypeNotAcceptableException` (`Accept: text/plain`), `HttpRequestMethodNotSupportedException` (PATCH, and PUT/DELETE on the collection).

**Q1. PUT/DELETE owner: 200 or 204? RESOLVED -> 204, no body.**

- [DOC] PUT 200 with an `Owner` body; DELETE 200 with an `Owner` body whose description reads "Owner details found and returned." (copy-paste). Sibling `PUT /owners/{id}/pets/{petId}` is documented 204 with no body.
- [OBS] PUT and DELETE return 204 with an empty body.
- [SRC] `OwnerRestControllerV1.updateOwner` and `deleteOwner` return `HttpStatus.NO_CONTENT` explicitly, so this is intent, not an accident.
- [FW] `clients/pet-types-api-client.ts` already asserts 204 for PUT and DELETE although the spec documents 200 for PetTypes too. The framework therefore already treats this service's 200 documentation for update/delete as a documentation defect.
- Recommendation: assert 204 and an empty body; record the spec as inaccurate (documentation defect). Reversible: if the spec is declared authoritative, the service is the defect and U-01/D-01 become red, with no other design change.

**Q2a. Is telephone exactly 10 digits? NEEDS_DECISION.**

- [DOC] `minLength 1`, `maxLength 20`, pattern `^[0-9]*$`.
- [SRC] `model/Owner.java`: `@Pattern(regexp = "^[0-9]{10}$", message = "Phone number must be exactly 10 digits")` on the entity (the DTO-level OpenAPI constraints do not include it).
- [OBS] 10 digits -> 201; 1, 6, 9, 11, 20 digits -> 500; 21 characters or empty -> 400 (rejected earlier by the DTO constraints).
- Discrepancy: the entity states an explicit, worded business rule that the contract does not. Evidence leans to "exactly 10 digits is intended and the spec is stale", but that is a requirement, so it is not adopted silently.
- Needed: choose (A) exactly 10 digits (spec to be corrected; 9/11/1/20 digits then expect 400) or (B) 1..20 digits (service to be fixed; 9/11/1/20 digits expect 201).
- Decidable now: 10 digits -> 201 and 21 digits -> 400 (both options agree). Hence OWN-C-13 is READY-PARTIAL and OWN-U-07 is BLOCKED.

**Q2b. Telephone violation returns 500. POTENTIAL_DEFECT -> expected 400.**

- [DOC] POST and PUT document 400 for bad requests; DTO-level violations (21 digits, non-digits) already return a 400 `ProblemDetail` with `schemaValidationErrors`.
- [OBS] Entity-level violation surfaces at persist time as `TransactionSystemException` -> caught by the catch-all -> 500. [SRC] confirmed by the advice (no handler for it).
- Under both options in Q2a, a client-input validation failure must not be a 500.

**Q3a. Invalid path ids and paging parameters. POTENTIAL_DEFECT -> expected 400.**

- [DOC] Path `ownerId` is `int32`, `minimum: 0`; GET/PUT/DELETE by id and `v2` list explicitly document 400. `v2` `size` has `minimum 1`/`maximum 100`, `page` `minimum 0`.
- [OBS] `-1`, `abc`, `1.5`, `99999999999`, `2147483648`, blank, `size=0`, `size=101`, `page=-1`, `page=abc` -> 500 (see root cause). `0` and `2147483647` -> 404, which is correct (valid but absent).
- Recommendation: assert 400. These scenarios are READY and will be red until fixed.

**Q3b. Malformed JSON and missing body. POTENTIAL_DEFECT -> expected 400.**

- [DOC] POST documents 400 'Bad request'. [OBS] `{bad json`, empty body, and a bad pet `birthDate` (`2020-13-45`) -> 500 (`HttpMessageNotReadableException`). Standard Spring behavior without the catch-all would be 400.

**Q3c. Unsupported Content-Type, Accept and method. NEEDS_DECISION.**

- [DOC] No 415, 406 or 405 anywhere. [OBS] `text/plain` body, `Accept: text/plain`, PATCH, and PUT/DELETE on `/owners` all return 500.
- 500 is wrong under every option. The exact code (415/406/405 as HTTP prescribes, or 400) is a requirement. Needed: pick the codes, or confirm that only `4xx` is required. Scenario OWN-C-20 splits accordingly (missing body ready, wrong Content-Type blocked). No scenarios were invented for Accept/405.
- Unverified hypothesis (cannot be tested here, only admin exists): a request by a user lacking `ROLE_OWNER_ADMIN` fails with `AccessDeniedException`, which the same catch-all would turn into 500 instead of 403.

**Q4. Empty v1 search returns 404. POTENTIAL_DEFECT -> expected `200 []`.**

- [DOC] `GET /owners` documents 200, 304, 500 only; 404 is absent. [SRC] `listOwners` explicitly does `if (owners.isEmpty()) return NOT_FOUND`: intentional code, but undocumented. [OBS] v1 no-match -> 404 with empty body; v2 no-match -> 200 with `{"content":[],"page":0,"size":20,"totalElements":0,"totalPages":0}`.
- Discrepancy: the contract says 200; v1 and v2 disagree on the same filter. Per CLAUDE.md the spec is primary, so 404 is recorded as a defect. If the team keeps 404, the spec must document it and OWN-L-03/L-04/D-02 follow; D-02 is already written to avoid depending on this.

**Q5a. Security. RESOLVED -> 401 on every endpoint without or with bad credentials.**

- [DOC] No `securitySchemes`, no 401/403; the `info.description` only says "If authentication is enabled, use admin/admin". [SRC] `security/BasicAuthenticationConfig.java` (`petclinic.security.enable=true`): `anyRequest().authenticated()` with HTTP basic; `playwright.config.ts` starts the container with `PETCLINIC_SECURITY_ENABLE=true`. [OBS] no credentials -> 401 with `WWW-Authenticate: Basic realm="Realm"`; a wrong-password request was also 401 (the earlier probe set recorded 401 for wrong credentials; my own re-check of that case was inconclusive because curl prompted for a password, so rely on the earlier probe and re-verify when A-02 is implemented).
- The missing documentation is a documentation defect, not a test blocker.

**Q5b. Authorization by role. NEEDS_DECISION.**

- [SRC] every owner operation has `@PreAuthorize("hasRole(@roles.OWNER_ADMIN)")`; the seed data (`resources/db/hsqldb/data.sql`) creates one user, `admin`, with `ROLE_OWNER_ADMIN`, `ROLE_VET_ADMIN`, `ROLE_ADMIN`. There is no endpoint to create users, and `.env` has only the admin account. A 403 test is impossible without provisioning a second user (database seed or a custom image), which is an environment change.
- Needed: decide whether to provision a limited-role user. Until then OWN-A-03 is BLOCKED. (No credentials were guessed.)

**Q6. 404 bodies. POTENTIAL_DEFECT -> expected `ProblemDetail`.**

- [DOC] GET by id, PUT, DELETE, pet and visit 404s all declare `ProblemDetail`. [SRC] owner controllers return a bare `new ResponseEntity<>(HttpStatus.NOT_FOUND)`; only the `DataIntegrityViolationException` handler produces a `ProblemDetail` 404. [OBS] owner-not-found 404s have an empty body; FK-violation 404s (unknown pet type, visit without date) have a body.
- Recommendation: every 404 scenario asserts the status only; the body contract is tested once in new scenario OWN-G-08 (red until fixed), so one defect is not repeated across scenarios and no assertion is weakened.

**Q7a. Unknown pet type id. NEEDS_DECISION.**

- [DOC] `addPetToOwner` lists 400 'Bad request' and 404 'Pet or Owner not found'. [SRC] a FK violation raises `DataIntegrityViolationException`, which the advice deliberately maps to 404. [OBS] 404 with title `DataIntegrityViolationException`, detail "data constraint violation".
- 404 is within the spec's list but its description does not mention pet types. Needed: decide 404 (current) or 400. OWN-PET-04 is BLOCKED.

**Q7b. Visit without `date`. POTENTIAL_DEFECT, direction undecided.**

- [DOC] `VisitFields.required = [description]`; `date` is optional with no stated default. [SRC] `model/Visit.java` has `@NotNull` on `date`. [OBS] 404 `DataIntegrityViolationException`.
- A 404 is wrong under any reading (nothing is missing). Whether the fix is a server default (201) or a required `date` (400, spec corrected) is a requirement. OWN-VIS-03 is BLOCKED.

**Q7c. Wrong-owner pet update and visit. POTENTIAL_DEFECT -> expected 404.**

- [DOC] PUT pet and POST visit both document 404 'Pet not found for this owner'. [SRC] `updateOwnersPet` loads the owner and the pet independently and never checks that the pet belongs to the owner; `addVisitToOwner` ignores `ownerId` entirely. `getOwnersPet` does check (`owner.getPet(petId)`).
- [OBS 2026-11-11] owner A, pet of owner B: GET via A -> 404; PUT via A -> 204 and the pet was renamed; POST visit via A -> 201.
- The documented expectation is explicit, so the scenarios are READY (red until fixed). Impact note: a client can modify another owner's pet through a mismatched URL.

**Q8a. `lastName` prefix semantics. RESOLVED.** [SRC] `SpringDataOwnerRepository`: `... WHERE owner.lastName LIKE :lastName%` (v1) and `LIKE CONCAT(:lastName, '%')` (v2): a prefix match. [OBS] `Dav` matches `Davisqx` and `Davis`; `Davisqx ` (trailing space) does not. The earlier note that `dav` failed to match as a prefix (old D16) was a case effect, not a prefix effect (corrected in Section 3).

**Q8b. `lastName` case and wildcards. NEEDS_DECISION.**

- [DOC] Only "Last name." [OBS] `davisqx` (v1 and v2) and `DAVISQX` (v1) do not match `Davisqx`; `Dav%` and `D_visqx` do match, because `%` and `_` are not escaped. Case sensitivity of `LIKE` depends on the database (the test image uses an in-memory DB; behavior on another database could differ).
- Needed: decide whether the filter is case-insensitive and whether `%`/`_` are literals. Until then those two sub-cases of OWN-L-04 are BLOCKED. Unicode case folding was not probed (depends on the same decision).

**Q9. 304 responses. RESOLVED -> not reachable, do not test.** [DOC] 304 is documented for GETs and DELETE. [OBS] a 200 carries `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` and no `ETag` or `Last-Modified`; `If-None-Match: *` and a future `If-Modified-Since` both return 200. No conditional-request mechanism was found in the owner controllers reviewed (the rest of the application was not searched, so this is "not reachable on the observed service"). The spec's 304 is a documentation inaccuracy. OWN-G-06 is N/A; recommend removing it.

**Q10. Seeded data. RESOLVED.** [SRC] `data.sql` seeds owners 1..10 into an in-memory database at startup. [OBS] 10 owners, ids 1..10, before and after probing; owner 1 is George Franklin with pet Leo. Tests must treat ids 1..10 as read-only. OWN-G-02 is READY but seed-dependent: a long-lived local container reused via `reuseExistingServer`, or Pets/Visits tests that mutate Leo, can break it, so assert stable owner fields only.

**Q11. Out of scope.** Concurrency, performance and very large payloads are excluded by design. This is a scoping statement; no investigation was needed.

**Q12. Items not previously probed. RESOLVED (probed).** `1.5` as id -> 500 (Q3a). v2 no-match -> 200 empty (OWN-L-13). `Accept: text/plain` -> 500, PATCH -> 500, PUT/DELETE on collection -> 500 (Q3c). HEAD `/owners/{id}` -> 200 and OPTIONS `/owners` -> 200 (nothing to assert). Request without `Accept` works. Unicode case-folding not probed (Q8b).

**Q13 (new). How should known-red tests be represented? NEEDS_DECISION.** CLAUDE.md forbids weakening assertions to turn tests green and requires API defects to be distinguishable from test defects. Not decided: leave them failing, or mark them `test.fail()`/`test.fixme()` with a defect reference. 11 scenarios plus the red parts of C-20 and PET-03 depend on this. Implementation can start before it is settled, because it does not change what is asserted.

**Q14 (new). Lenient type coercion (D13). NEEDS_DECISION.** [DOC] `telephone` is a string. [OBS] a JSON number is accepted and stored as a string (201). Spring Boot's Jackson coerces scalars by default; whether that leniency is accepted or the API should return 400 is a requirement. OWN-C-18 is BLOCKED. Not verified: how booleans and objects behave (an object would likely hit `HttpMessageNotReadableException` -> 500, Q3b).
